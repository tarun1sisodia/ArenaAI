## Schema and migration ownership

### `public.inquiries`

`0008_create_audit_notifications_inquiries.sql` creates the base table with `id`, `name`, `phone`, nullable `email`, required `message`, nullable `trip_interest`, and `created_at`. `0009_add_indexes_and_rls.sql` enables RLS. `0014_inquiry_status_and_notes.sql` adds required `status` defaulting to `new`, required `notes text[]` defaulting to `{}`, and required `updated_at` defaulting to `now()`, plus status and created-at indexes. `0016_comprehensive_rls_policies.sql` adds a service-role-all policy and an anonymous insert policy (`WITH CHECK (true)`).

Live inventory (`reports/live-schema-inventory.md:352-365`) confirms: `id uuid NOT NULL` with no database default, `name text NOT NULL`, `phone varchar NOT NULL`, `email varchar NULL`, `message text NOT NULL`, `trip_interest text NULL`, `created_at timestamptz NOT NULL DEFAULT now()`, `status varchar NOT NULL DEFAULT 'new'`, `notes text[] NOT NULL DEFAULT '{}'`, and `updated_at timestamptz NOT NULL DEFAULT now()`.

Backend ownership is `InquiryRecord` in `backend/src/types/domain.ts:343-365`; repository contract is `Repositories.inquiries` in `backend/src/db/types.ts:237-242`; Zod creation contract is `CreateInquirySchema` in `backend/src/modules/inquiries/inquiry.schema.ts:3-29`; persistence is `mapInquiry` in `backend/src/db/postgres.ts:313-325` and the `inquiries` repository at `postgres.ts:1279-1337`.

## Writers, readers, and endpoint chains

### Inquiry chain

1. **Customer/public writer:** `POST /api/v1/inquiries` (`inquiry.routes.ts:8-11`) parses `CreateInquirySchema`, then `inquiry.service.ts:10-23` builds the full `InquiryRecord` (`newId`, optional fields as null, `status='new'`, `notes=[]`, timestamps) and calls `db.inquiries.create`.
2. **Backend persistence:** PostgreSQL inserts all 10 live columns in `postgres.ts:1280-1290`; `mapInquiry` maps snake_case back to the domain model.
3. **Admin reader:** `GET /api/v1/ops/admin/inquiries` is role-guarded in `admin.routes.ts:28-36`/controller and calls `admin.service.ts:79-87`, which returns both `items` and `inquiries`. The repository supports status/search pagination (`postgres.ts:1311-1336`).
4. **Admin writer:** `PATCH /api/v1/ops/admin/inquiries/:id` is role-guarded; `AdminUpdateInquirySchema` permits only status and one note. The service fetches, mutates status/notes and `updatedAt`, and the repository updates the full mutable inquiry payload (`postgres.ts:1292-1305`). The page advances `new → contacted → quoted → converted → closed`; `resolved` and `spam` remain API-valid statuses but are not in the page's normal `FLOW`.
5. **Customer readers:** There is no customer-facing inquiry read route and no inquiry confirmation lookup. `ContactCard.tsx:82-87` does persist to the API and reports success, but `ContactPage.tsx:50-68` currently only builds a WhatsApp URL and calls `window.open`; it does **not** call `createInquiry`. This is a source/report divergence: audit docs claim ContactPage was wired in `AUDIT_PROGRESS.md:170-174`, but the current file is still WhatsApp-only.
6. **Admin display:** `admin/src/lib/api.ts:152-189` maps API fields to the admin model; `InquiriesPage.tsx` shows name, phone, derived type/subject, message, status and notes. It does not display email or the raw `tripInterest` separately.

### Rental chain

1. **Customer/public writer:** `POST /api/v1/rental-enquiries` (`rental-enquiry.routes.ts:4`) parses `CreateRentalEnquirySchema`; `rental-enquiry.controller.ts:9` calls the service and returns only `{ref, phone}` for customer confirmation. `rental-enquiry.service.ts:9-12` normalizes optional email/note to null and creates a `new` record.
2. **Backend persistence:** PostgreSQL inserts all 15 columns in `postgres.ts:1274`; `mapRentalEnquiry` maps snake_case to the domain model. Date strings are returned as `YYYY-MM-DD`.
3. **Admin reader:** `GET /api/v1/ops/admin/rental-enquiries` requires `ADMIN_ROLES`, validates status/car/date/search/page filters, and returns `items` plus `rentalEnquiries` (`rental-enquiry.controller.ts:10`). SQL supports status, car tier, pickup-date range, name/phone search, count, and pagination (`postgres.ts:1277`).
4. **Admin writer:** `PATCH /api/v1/ops/admin/rental-enquiries/:id` requires an admin role and permits only a valid status and/or one note. The service appends notes and updates the timestamp; repository SQL updates only `status`, `notes`, and `updated_at`, preserving customer-submitted fields.
5. **Customer readers:** `RentalPage.tsx:10-14` reads the response and shows `ref` and canonical phone; there is no public list/read path. The customer receives no status/quote object because availability and payment intentionally remain phone-led.
6. **Admin display:** `RentalRequestsPage.tsx` displays ref, customer, phone, car/date, status, email, driver preference, customer note and operator notes; it provides tel/WhatsApp links and workflow advancement.

## Foreign keys and cross-table lifecycle

Neither target table has a foreign key to `profiles`, `bookings`, `customer_booking_intents`, or any other table in the live inventory. The inventory lists no target-table FK entries. Consequently:

- An inquiry or rental request is an **independent lead**, not a booking or payment record.
- `converted` (inquiry) and `done` (rental) are operational statuses only; they do not create or point to a booking.
- There is no referential integrity or database-level audit link from an operator note/status change to `admin_audit_logs`; the admin services update the row directly. If conversion/attribution matters, add an explicit nullable `resulting_booking_id`/lead-event model only after a reviewed product decision, not as an audit-side mutation.
- Delete/update behavior is therefore simple: no child rows cascade; current application exposes no delete operation for either table. `rental_enquiries` has an update timestamp trigger; `inquiries` relies on application timestamps.
- RLS is enabled on both. `inquiries` has service-role-all plus anonymous insert policy from `0016`; `rental_enquiries` has service-role-all only, so direct anon Supabase writes are blocked and backend service-role writes are the intended path.

## Confirmed mismatches and severity

### 1. High confidence P2 — Contact page does not persist to `inquiries`

**Evidence:** `react/src/pages/ContactPage.tsx:50-68` sets submitted state and opens `https://wa.me/...`; it imports neither `createInquiry` nor `getApiBaseUrl`. In contrast, `ContactCard.tsx:20,75-87` calls `createInquiry`, and `react/src/services/api.ts:276-293` implements the endpoint. The current source contradicts `docs/project/AUDIT_PROGRESS.md:170-174` and the “resolved” statement in `docs/project/AUDIT_FINDINGS.md:418-432`.

**Impact:** Leads submitted through the dedicated Contact page bypass the `inquiries` table and cannot appear in the admin inbox. The page's success state means “WhatsApp window requested,” not “database inquiry persisted.” WhatsApp itself may still receive the lead, but it is outside the audited database lifecycle and not queryable by operators.

**Recommended fix:** Either wire ContactPage to the existing `createInquiry` adapter, packing its service/date/pickup/vehicle fields into the validated `message` and setting `tripInterest`, or explicitly remove/rename the page form as WhatsApp-only. Add a customer-form contract test that asserts one valid ContactPage submit calls `POST /api/v1/inquiries` and a short message is adapted to the backend minimum.

### 2. P2 — `rental_enquiry_ref_seq` is dead code and reference generation is collision-prone

**Evidence:** `0021_create_rental_enquiries.sql:2` creates `rental_enquiry_ref_seq`; `rental-enquiry.service.ts:11` instead uses ``RNT-${year}-${String(Date.now()).slice(-6)}``. `ref` is unique in the database. Concurrent requests sharing the same millisecond suffix can violate the unique constraint, and the injected application clock is not used for the suffix. This is a deterministic code/schema mismatch even though no collision is visible in the single live row.

**Recommended fix:** Use `nextval('rental_enquiry_ref_seq')` in a repository-generated reference, or use a UUID/time-safe reference with an explicit retry on unique conflict. Keep the `UNIQUE(ref)` constraint and add a concurrency test.

### 3. P2 integrity gap — inquiry status is unconstrained at the database layer

**Evidence:** `0014_inquiry_status_and_notes.sql:2-4` adds `status VARCHAR(30) NOT NULL DEFAULT 'new'` but no CHECK. `InquiryStatus` and `AdminInquiryQuerySchema` define a seven-value union. Rental status has a DB CHECK in `0021:15`, so the two otherwise parallel lead tables differ.

**Impact:** Direct SQL/service-role code can persist an arbitrary status that backend/admin Zod contracts cannot list or transition. No invalid live value was observed because `inquiries` has zero rows.

**Recommended fix:** Add a reviewed migration with a CHECK matching the canonical application statuses after deciding whether `converted`, `resolved`, and `spam` are all required. Before applying it, scan/repair any out-of-union values; this audit did not mutate production.

### 4. P3 — blank optional `tripInterest` is not normalized before persistence

**Evidence:** `CreateInquirySchema` trims `tripInterest` and applies only `.max(160).optional()` (`inquiry.schema.ts:21-26`); unlike rental `email`/`note`, it does not convert `''` to undefined. `inquiry.service.ts:18` uses `input.tripInterest ?? null`, which preserves `''`. The mapper later treats a falsy value as null (`postgres.ts:320`), masking the storage inconsistency on reads.

**Recommended fix:** Add `.or(z.literal('')).transform(v => v || undefined)` or an equivalent trim/nullable transform; add a unit contract test asserting blank input persists as NULL. This is low impact and no live row currently exists to show it.

### Not defects

- Optional inquiry email/trip interest and rental email/note are intentionally nullable for phone-first/contact-first leads; no false “missing data” defect should be raised.
- Empty `notes` arrays are intentional before an operator adds a call summary; the one live rental row is `done` with no operator note, which is valid.
- Rental customer note `NULL` is intentional and confirmed live.
- Status changes do not create bookings because no FK/conversion workflow is defined; this is an explicit domain boundary, not a broken FK.

## Bounded lifecycle test plan (read-only in production)

Production mutation must remain prohibited for this audit because a valid customer-form POST and admin PATCH would create/update real lead data and a valid admin status transition would alter operational state. Run the following against an in-memory repository or disposable local/test database, not Supabase production:

1. **Inquiry contract:** parse a valid ContactCard/ContactPage-adapted payload; assert Zod normalization, `status='new'`, `notes=[]`, nullable optional fields, and one repository insert with all live columns.
2. **Inquiry admin lifecycle:** seed an in-memory record; call admin update with status `contacted`, then add a note; assert status, appended note, and increasing `updatedAt`; test invalid status rejection and invalid note rejection.
3. **Rental contract:** parse a valid payload with formatted phone, empty email/note, same-day dates, driver true/false; assert canonical phone, email/note NULL, status `new`, and notes `[]`.
4. **Rental admin lifecycle:** seed a record; advance `new → contacted → quoted → done`, append a note, and assert customer fields remain unchanged while `updatedAt` advances.
5. **Reference uniqueness:** run concurrent rental creates using a deterministic clock; demonstrate the current `Date.now()` suffix can collide, then verify the proposed sequence/UUID implementation produces unique refs.
6. **Database-only read checks:** in a disposable database, assert rental date/status/car constraints and the inquiry status CHECK proposed above. In production, only the already-completed read-only MCP count/null query is permitted.

## Recommended fixes, in dependency order

1. Restore/wire the dedicated ContactPage to `POST /api/v1/inquiries` (or make its WhatsApp-only behavior explicit), then add a frontend/backend contract test.
2. Replace rental reference timestamp suffix generation with the existing sequence or a collision-resistant reference, retain the unique constraint, and add concurrent-create coverage.
3. Decide canonical inquiry status vocabulary; add a database CHECK after an offline invalid-value scan and migration review.
4. Normalize blank optional `tripInterest` to NULL and add a unit test.
5. Consider recording lead-to-booking conversion and operator changes in an explicit, reviewed audit model only if operations require that relationship; do not infer a booking FK during this read-only audit.
6. Keep production validation read-only until the above tests pass in memory/disposable DB and the separate deployment owner approves any schema migration.
