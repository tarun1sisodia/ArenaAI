# Table audit 12 — `public.local_sightseeing_packages`

**Audit date:** 2026-10-06  
**Scope:** database contract, migration, backend model/schema/mapper/repository/service/controller/routes, admin API/form/page, fare calculation, customer/public readers and publication artifact.  
**Safety:** read-only audit. No production writes, migrations, deletes, webhook replays, or external submissions were performed.

## Executive result

The table has **3 live rows**: **2 `published` and 1 `archived`**, all with `is_active = true`. A read-only Supabase SQL check returned no NULLs for `parking_note` or `extra_rates` and no empty `package_code`, `name`, `covers`, or `{}` `fleet_prices`. The existing inventory independently records the same row count/status split and RLS disabled state.

The normal admin-to-PostgreSQL field chain is aligned: `0024_dossier_content.sql` → `LocalSightseeingPackageRecord` → strict Zod input schema → service transformations → `mapLocalPackage` → PostgreSQL insert/update SQL. The admin page sends the snake_case payload expected by Zod, and the public build artifact contains the two currently published rows.

Two important gaps remain:

1. **High — RLS is disabled.** The live inventory and prior Supabase advisory evidence report `local_sightseeing_packages` with RLS disabled. Direct Supabase access is therefore not protected by table policies; remediation must be a separately reviewed policy migration, not a bare `ENABLE RLS` change.
2. **Medium — `is_active` is not part of public eligibility.** Both the public manifest and public detail controller filter/check `status = 'published'` only. An item can be `published` while `is_active = false` (the admin/backend contract allows this), yet it will still be emitted publicly and used by the public detail endpoint and fare lookup. Current live rows do not demonstrate the bad state, but the code path demonstrably permits it.

There is also a **configuration-dependent freshness risk**: public pages are generated from `generated-published-local-packages.json`; publish/archive/price edits call `PAGES_DEPLOY_HOOK_URL`, but the hook is optional and only warns when unset/failing. The current checked-in artifact has the two live published rows, so this is not a current data mismatch.

## Backend ownership and alignment

### Migration

`backend/migrations/0024_dossier_content.sql` creates the table with the columns/defaults/checks listed above and an index on `status`. Seed rows are `agra-standard-sightseeing` and `agra-extended-city-tour`, both inserted as draft (`0024`, lines 319–342). The live state shows the standard row later archived, extended row published, and one additional published row created later. No migration adds a local-package FK to bookings or catalog tables.

### Domain type

`backend/src/db/dossier-types.ts:6–22` defines `LocalSightseeingPackageRecord` with camelCase equivalents for every column. Nullable types are explicit for `parkingNote` and `extraRates`; all DB `NOT NULL` fields are non-nullable in TypeScript.

### Zod contract

`backend/src/modules/local-packages/local-packages.schema.ts:20–63` is strict and translates the admin snake_case wire contract. It validates/sanitizes text, validates code format, bounds duration and included distance, requires positive finite fleet values, allows nullable/omitted `extra_rates`, defaults `use_per_km`, `night_charge_inr`, and `is_active`, and validates status/query parameters.

The update schema is `base.partial()` with status re-added as optional. `package_code` is accepted by Zod but the service rejects changes after creation with `PACKAGE_CODE_IMMUTABLE`.

### Service

`backend/src/modules/local-packages/local-packages.service.ts:14–129`:

- `toRecord` maps every create field, converts omitted nullable fields to `null`, sets status draft/defaults and timestamps.
- Create checks code uniqueness, persists through `db.localPackages.create`, and requests a frontend rebuild if initially published.
- Update merges every field, preserves omitted nullable values, prevents code changes, refreshes `updatedAt`, and rebuilds when pricing JSON changes on a previously published row.
- Publish/archive set status and refresh `updatedAt`, then request a frontend rebuild.
- Remove is only allowed for draft rows; published/archived content must be archived instead.

### Mapper and repository SQL

`backend/src/db/postgres.ts:49–67` maps all 15 columns; `parking_note` falsy values become `null`, JSON fields are typed/cast, and timestamps are ISO strings. `backend/src/db/postgres.ts:873–922` inserts and updates every mutable table column, reads by UUID or code, filters list by status/query, orders by `duration_hours`, and deletes by ID. The SQL has no dropped local-package field or alias mismatch.

The in-memory repository (`backend/src/db/memory.ts:565–610`) supports isolated create/update/get/list/delete lifecycle tests and does not touch production data.

## Foreign keys and cross-table lifecycle

- **Direct FK relationships:** none from or to `local_sightseeing_packages` in the inspected live inventory/migrations.
- `bookings.package_id` is a nullable `varchar` and has no FK to this table; it can hold a package code/identifier through the booking service contract.
- `bookings.booking_selection` is nullable `jsonb` and carries the logical customer selection (`kind: local`, `id`, `source`, optional `slug`/legacy `localPackageKey`). This permits historical bookings to retain selection context even if a package is later archived, but it does not enforce referential integrity.
- Public URLs use `package_code` as a slug; service immutability protects the URL after creation.
- Fare reads are status-gated and therefore stop using archived rows. A package can remain in the database for history while new fare calculations cannot select it.
- Archive does not delete data. Draft-only deletion is allowed; there are no dependent FK rows whose cascade behavior must be considered.
- The local-package table is separate from `catalog_items`; prior reports identify these as dual content sources. No FK or automatic synchronization exists between them. For local packages, dossier table + manifest is the authoritative path in the inspected code.

## Mismatches and severity

### M-01 — Published-but-inactive rows are publicly eligible (**confirmed defect, medium**)

**Evidence:** `local-packages.controller.ts:19–30` and service list/repository SQL use `status='published'` only; `fare.service.ts:150–154` also checks status only. The DB has a separate `is_active NOT NULL` field, and update/create schemas/repository persist it. Therefore a row with `status='published', is_active=false` is still returned by `/api/v1/local-packages/manifest`, returned by `/by-code/:code`, and used for fare lookup. Current live rows all have `is_active=true`, so no current bad row is claimed.

**Fix:** define one eligibility predicate (`status = 'published' AND is_active = true`) and apply it to public manifest, public detail, fare lookup, and any future sitemap/build source. Decide whether admin list should continue showing inactive published rows for repair. Add regression coverage.

### M-02 — Business bounds are enforced only in Zod, not DB; admin distance UI is looser (**contract/data-integrity gap, medium-low**)

**Evidence:** migration has no checks for `duration_hours`, `included_km`, JSON shape, or positive fleet values. Zod enforces duration 1–48, included km 10–1000, positive finite fleet/extra rates; the admin `NumberInput` uses `min={1}` for included distance, so entering 1–9 reaches the API and is rejected rather than being prevented in the form.

**Fix:** keep backend validation as source of truth; align admin min to 10 and show inline errors. If direct Supabase/service-role writers are in scope, add reviewed DB checks/JSON validation or make all writes go through the backend. Do not add a production migration as part of this audit.

### M-03 — Public content freshness depends on optional deploy-hook configuration (**configuration blocker/risk, medium**)

**Evidence:** `backend/src/shared/deploy-hook.ts` returns after warning if `PAGES_DEPLOY_HOOK_URL` is absent and only warns on failed hook responses. The public site resolves local pages from the build-time `generated-published-local-packages.json`, not from the public endpoint at request time. The current artifact matches current live published rows, so this is not a present mismatch.

**Fix:** verify `PAGES_DEPLOY_HOOK_URL` and hook success in deployment configuration, or add a bounded runtime revalidation strategy. A publish operation should have observable build completion/verification, not only fire-and-forget warning logs.

### M-04 — RLS disabled (**confirmed security defect, high**)

**Evidence:** `reports/live-schema-inventory.md` table summary lists `local_sightseeing_packages` with RLS `DISABLED`; prior reports list it among 12 affected tables. With Supabase direct API exposure, database authorization is not enforced at table level.

**Fix:** separately design and review policies: public read only for published/active content (or keep reads backend-mediated), no anon/authenticated direct writes, service-role/backend write path, and explicit tests for anonymous/authenticated/admin/backend roles. Do not blindly enable RLS without policies.

## Intentional NULLs/empty values

- `parking_note = NULL`: intentional omission when no custom note; public reader has a safe fallback.
- `extra_rates = NULL`: intentional when no extra-hour/km tariff is published; fare calculation treats absent per-km override as undefined.
- `status = draft/archived`: intentional lifecycle states; only published content is public/fare-eligible.
- `night_charge_inr = 0`: intentional no-charge value, not missing data.
- `use_per_km = false`: intentional fixed package pricing mode in all current rows.
- No current live row has these nullable fields NULL or relevant text/JSON empties, so the audit does not infer a production defect from absence.

## Bounded lifecycle validation

Because this is a production-connected content table and the instructions prohibit production writes, the production test must remain **read-only**. The allowed bounded plan is:

1. Read-only query counts/status/nulls (performed; result above).
2. Use the existing in-memory repository and service with a disposable record to assert create → get by code → update pricing → publish → list published → archive → list excludes archived → draft-only delete. Assert mapper-equivalent nullable semantics and code immutability. This does not mutate Supabase.
3. Run schema/contract tests and backend typecheck; do not call production admin endpoints with POST/PATCH/DELETE.
4. For deployment verification, issue only GETs against public manifest/detail and compare returned published codes to the current build artifact. Do not trigger a rebuild or replay any external event.
5. A future controlled staging test (not this audit) should verify `is_active=false` is excluded once M-01 is fixed, and that a publish changes both API manifest and generated public page after the configured hook completes.

The existing unit test at `backend/tests/unit/fare.engine.test.ts:212–223` is useful coverage for the legacy fallback but is insufficient for live local-package row resolution and does not exercise lifecycle state transitions.

## Recommended fix order

1. **Security:** design reviewed Supabase RLS/policies for public published-active read and backend/admin write; test roles before applying a migration.
2. **Eligibility:** centralize `published && is_active` and apply it to manifest, detail, fare, sitemap/build filtering, and any future public reader.
3. **Admin UX/data validation:** set included-km UI minimum to 10, render `is_active` control if the field is intended to be operator-managed, and surface Zod validation errors inline.
4. **Integrity:** decide whether DB-level checks for duration, included km, fleet JSON, and extra-rate JSON are required for all writers; if yes, add a reviewed migration only after staging verification.
5. **Freshness observability:** require/monitor `PAGES_DEPLOY_HOOK_URL`, expose hook failure to the operation that published content, and verify generated artifact/public page after deploy.
6. **Regression tests:** add in-memory lifecycle tests and public eligibility tests for status and active flag, plus a manifest snapshot test proving archived/inactive rows are excluded.
